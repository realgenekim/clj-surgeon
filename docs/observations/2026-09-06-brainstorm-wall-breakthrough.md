# Wall-clock breakthrough brainstorm (Gene, 2026-09-06 20:5xZ: "Read again goals and vision, and do wild brainstorming on how we can get performance breakthrough on wall clock and materially makes a difference… brain storm and prototyping. And ethnographic study of how real coding sessions work.")

## The constraint the receipts impose
Every measured Surgeon arm tonight put the server at ~2% of the wall. Wins came only where the route DELETED actor work (constructing N edits; trusting one receipt). So a breakthrough is not a faster tool; it is a route that removes whole phases of the actor's loop: orientation (8–25 s/arm), composition (10–45 s), verification (15–38 s incl. cold JVMs and own-oracle bugs), repair (20–30 s of own-test fixes in whole-task pairs).

## Fable's candidates, ranked by the size of the phase they delete
1. VERIFY INSIDE THE CALL (deletes verification, 15–38 s/edit; the largest measured phase). The call runs the repository's real tests server-side on a warm runner and returns pass/fail with expected/actual inline; the receipt is the proof the actor was going to construct anyway. Prototype tonight: measure edit+verify wall vs native verify on the-gene-maven; find why the `fast` profile rolled back earlier.
2. KILL ORIENTATION with a per-repo SURGEON BRIEF (deletes 8–25 s/arm and the repeated per-file alias reads): one generated file (namespaces, aliases, test command, owner index, hashes) the plate points at; one read replaces 3–5 exploratory calls.
3. REFUSAL RETURNS A SUBMITTABLE PLAN (deletes repair round trips): every refusal's next_call must post back verbatim; extract-E needed 3 calls where 1 was possible (inb-b3b6d1).
4. WARM SERVER-SIDE TEST RUNNER with changed-ns test selection (deletes cold JVM starts: native paid 18–32 s ×3 on its own oracles): the nREPL probe idea owned by the server, never the agent.
5. AGENT-NATIVE INPUT (deletes the learning tax): accept the agent's own apply_patch/unified diff as admit input; the receipt (with tests inside) is the value; the recovery pilot's caller wanted exactly this.
6. WHOLE-LOOP TARGET, not per-edit: real sessions are edit→test→fix loops; the meter that matters is loop time; the ethnography of real sessions (running) says which phase dominates there.

## Wild ones (unmeasured, stated so they can be killed)
- Speculative execution: the server applies the edit and runs the tests BEFORE the agent asks, on the agent's visible intent (the prepared plan), and hands back a diff+receipt the agent only reads.
- Test-selection oracle: from the structural index, the server names the minimal test set for a change and runs only that; verification wall falls with the size of the change, not the repo.
- One-call task shapes: "rename/move/migrate X to Y across the repo, verified" as a single verb whose receipt includes tests — the alias route already is this; extend to the two or three next shapes only when a real task shows up (kill switch applies).
- Session-level receipts: the agent's whole session gets a running receipt (what was written, verified, remains), so the end-of-task "did I finish?" re-verification (extract-E: 28–38 s) is a read.

2026-09-06 21:01Z. I reread the vision: the durable asset is a small deterministic kernel that lets the model express intent cheaply. My larger hypothesis is that the tool should preserve decisions as executable data across discovery, editing, proof and handoff. Every time we translate the same decision back into prose or manually reconstructed JSON, we create another opportunity to think, mistype and re-check it.

The wild aperture, ranked by the work each could remove:

1. **An executable change conversation.** A request or result becomes a local immutable value. The next operation consumes that value, not a model's reconstruction of its fields. Example: inspect → select the named owners → supply only replacement intent → apply with the original guards. This could remove entire bookkeeping returns; the guard still refuses stale evidence. Some existing plans already do this—measure their missing handoffs before adding a new API.
2. **Proof as a dependency graph.** Record what each check actually read and verified. After an edit, rerun invalidated checks; reuse unrelated valid results with explicit coverage. Repository-declared check dependencies first, not a guessed “changed namespace means these tests” heuristic. This is a harder systems bet, potentially valuable over a long session; startup and invalidation belong in its bill.
3. **Native action plus continuation.** One declared operation carries the patch and the existing test argv. The kernel performs both and returns either a complete receipt or actual assertion details. No automatic command invention from Makefile text. This buys one boundary only if the agent would otherwise return between patch and test; our strongest native controls already batched them.
4. **One structural relation over a set.** The agent supplies a Clojure function over already selected owners; the kernel materializes exact edits and validates preservation. Avoid serializing an N-owner edit list back through the model. Native scripting is the competing arm; an evaluator that merely reprints every owner loses.
5. **A live, tiny repository contract.** Hash-bound facts the actor repeatedly needs: which checked-in command verifies this change, where a request dispatches, what must remain untouched. Incremental invalidation, no speculative repository encyclopedia. Charge preparation and compare with a checked-in plain-text brief available to native too.
6. **Failures delivered at the repair site.** Assertion name, expected/actual, candidate identity and whether bytes changed, in the first result. The dead-report path we observed is a real defect. The entire surrounding30–60s is not a proven saving from fixing it.
7. **Speculative proof before the model asks.** After an authorized local edit, begin already-declared read-only checks while the actor reviews. Never publish speculative writes or hide resource contention. Cancellation/waste counts; compare with native background tests.
8. **Executable examples, not re-authored examples.** The exact request that ran supplies documentation, a replayable sample and the validator witness. A tiny native script may be the whole answer. If so, ship the script or convention rather than making it another Surgeon feature.
