# Sol red-team: `tighten-the-loop`

Advice only, 2026-09-08. I changed no skill, command, doctrine, plate, branch, or schedule.

## Verdict

**NO-GO as an installed seat skill.** The draft has the right invariant—improvement may change machinery but may not change its own authority or evidence—but it currently describes a fleet contract that does not exist. A fresh Claude or Codex cannot execute the daily unit from this text alone, and the only installed `seat-receipt` explicitly self-builds a v0 subset that omits the protected denominator and participation evidence. Install it only after the concrete binding, independent recorder, command contracts, Andon entrance, and house-rule rulings below are real and have survived one fresh Claude cell and one fresh Codex cell.

The name survives. **`tighten`** is short, imperative, Gene's word, and correctly suggests making an existing loop faster and more scrutinized rather than declaring it perfect. If it must be replaced, use **`ratchet`**, which names the irreversible mechanism more precisely.

## 2. Fixed-point attack: builder changes the oracle

Construct this case:

1. Epoch E's output still contains stale copied prose. Oracle O correctly fails it. The complete accepted wall is 120 seconds and apparatus share is 58/100 leaf actions.
2. The builder changes the product by zero bytes, edits O to stop checking stale prose, and edits the action classifier so the oracle invocation is counted as useful work. O' now passes; reported wall is 92 seconds and apparatus share is 47/100.
3. The dashboard says faster and clean, but there was no repair. The builder improved the meter by deleting the obligation and moving its denominator.

**The written CHANGE RULE refuses this at the specification level.** It freezes acceptance, oracle, classifier, observer, harness, argv, clock endpoints, task set, and denominator in the current epoch. The builder must keep E as reference; old and candidate instruments run the same frozen positive and negative cases; the triggering counterexample must be included; every changed verdict must cite approved intent or Gene's explicit ruling; changed instruments get a new epoch and fresh matched controls. O fails the retained stale-prose case while O' passes it. With no product repair and no ruling changing meaning, the steward must refuse qualification. The better scalar cannot promote the candidate.

That is a real fixed point: **authority over meaning and evidence remains outside the optimized machinery**. It is not a frozen implementation.

**The installed system does not enforce that refusal.** The current receipt hashes the runners but does not bind the frozen case inputs, old/new verdict matrix, assignment manifest, classifier, raw event range, independent steward signature, or ruling. Its corpora and generator are writable by the same `forge` account that is graded. The rule also assumes an already trusted first epoch and named independent owners; neither is instantiated. Before first installation, Gene must ratify epoch E's meaning and appoint the steward/recorder, or “current trusted package” is circular.

## 3. Protected denominator

The prose chooses the right denominator: prospectively assigned requests through independent acceptance, every assignment and attempt retained, pending work aging, and setup/recovery/waits inside the clock. That makes the common cheats visible.

It is **not un-gameable by the reporting seat today**:

- the seat can run the receipt after omitting or truncating its own event source;
- one wrapper call can hide twenty subprocess decisions unless the recorder observes the process/event tree outside the subject;
- the seat can omit an assignment before the manifest is externally sealed;
- a same-account “independent” process has the same write authority over runner, corpus, records worktree, and evidence;
- v1 permits explicit `unknown`, but there is no executable verdict rule proving that a required unknown bars `observed`;
- installed v0 contains no assignments, attempts, clocks, action window, denominator, acceptor, or independence fields at all.

Do not call it un-gameable. Call it **tamper-evident under an independently controlled assignment and event recorder**. Require the recorder to seal task ID, challenge nonce, intent/acceptance hash, subject session, start time, and expected event sources before disclosure; seal terminal events independently; reject `observed` when coverage is incomplete or the producer shares the subject's write authority. The seat may emit claims, but it must not choose the population, clock, event boundary, acceptance, or retained bytes used to grade those claims.

## 4. Forged seat receipt

A seat that never consumed `tighten-the-loop` can run today's `/home/forge/bin/seat-receipt` and obtain `on_loop=true` when routing bytes match, both corpora pass, and disk has 15 GB remaining. That is a configuration/corpus receipt, not participation. The program says so honestly, but SKILL step 1 overclaims that it records effective prompt, observation coverage, job heartbeat, and stop scopes.

No self-populated field prevents forgery. The field that makes non-participation detectable must be an **externally issued participation attestation**, not merely another subject string. Add:

```text
participation.attestation = {
  issuer_id, issuer_key_id, assignment_challenge_id,
  subject_seat_id, subject_session_id, launch_event_hash,
  effective_prompt_hash, consumed_at,
  first_task_event_hash, covered_event_range_hash,
  issued_at, signature
}
```

The independent recorder issues the challenge before launch, observes the launch/session and prompt uptake outside the subject, and signs the binding. The receipt verifier checks the issuer against the prospective roster and rejects replayed challenge/session pairs. Missing, invalid, self-issued, shared-write-boundary, or replayed attestation forces `configuration-only` or `unknown`. Existing `prompt.uptake_evidence` points at the right fact, but without issuer, challenge, causal session binding, and signature it is forgeable prose. `owners.independence` should disclose the trust boundary; it cannot substitute for the attestation.

## 5. House-rule collisions

1. **Andon:** The draft gets scope, fail-closed resume, five-minute mayor acknowledgment, and direct authority mostly right. It fails the house requirement that any seat can pull with **one command** and no permission/mayor in the path. `alert_route` names channels, but `commands` omits an Andon entrance and the daily steps say only “use the registered cord.” Until an absolute command plus delivery receipt is in every binding and a missing route itself closes the implicated authority, the skill cannot promise Andon.
2. **Ratchet:** “Every load-bearing fix carries its ratchet” is weaker and less testable than the house rule because the builder can call a fix non-load-bearing. Require either an executable recurrence-prevention witness or a recorded `ratchet-impossible` decision with independent owner and next action. Expected protection is not a defect and needs no fix; an actual fixed defect cannot disappear by classification.
3. **Doctrine versus plate:** The documents correctly say plate bytes and current-session uptake matter. The procedure orders landing before affected-seat delivery, while house rules say a boot-affecting doctrine change is not done until the canonical block is regenerated, announced, installed on every carrying account, checked at the consumer, and kept under a tripwire. The current receipt checks a routing block from the landing checkout, not this skill's installed resolution or current-session consumption. Distinguish “source branch landed” from “fleet change delivered”; never issue the latter verdict before consumer proof.
4. **Fable clause:** A Fable main loop specs, delegates, verifies, and gates; it does not type implementation. “Repair one earned batch” lacks that role gate. Say explicitly that Fable delegates the builder work and independently verifies the diff and command.
5. **Mayor clauses:** Selection of the hill/design must go independently to Fable and Sol; implementation from an Opus mayor goes to Codex Sol. The draft has the operator freeze an actionable selection and then run a builder without identifying this split. `ledger-to-findings` can mechanically project a prospectively approved selection; it must not silently make the selection. The mayor may schedule and land after independent selection/review.
6. **Delegated commits:** The house delegation protocol says agents never commit or push. The actual `round` prompt tells Codex to commit on the branch and the runner checks that commit. This is a direct unresolved contradiction. Change `round` so the supervised runner, not the delegated builder, creates the commit after verification, or obtain and publish an explicit doctrine exception before installation.
7. **Frozen public `main`:** The draft correctly names `MCP/main` and keeps public `main` frozen. Keep that project-specific clause. Remove the generic-other-repository implication until `land` is actually bound per repository.

The design of record already says boot/proof contradictions must be ruled on before generating the block everywhere. The skill's rollout prose says the same, which is itself a reason not to install it yet.

## 6. Length and voice

The imperative voice is good when it names an executable invariant. It becomes misleading when “run,” “use the binding,” and “the recorder retains” describe absent infrastructure. The 141-line SKILL is also carrying a design report, scar catalogue, rollout plan, and bibliography. A seat skill should be the shortest executable contract; CHANGE-RULE and SEAT-RECEIPT already own the detail.

Cut it to about **112 lines** without dropping a rule:

- Replace the repeated seven-line fixed-point summary with a two-line mandatory pointer to CHANGE-RULE.
- Replace the ten-line scars table with one pointer; every operational correction already appears in the daily steps, parent skill, or CHANGE-RULE.
- Move the first-two-weeks rollout plan back to the design of record; keep only “deadlines never pass gates” and the qualification boundary.
- Collapse sources to the design, parent, and two normative companion files. Historical receipts belong in those documents, not the runtime skill.
- Do not cut the second-encounter rule, denominator definition, correctness tripwire, Andon scope, or configuration-versus-behavior distinction. Those are the skill.
