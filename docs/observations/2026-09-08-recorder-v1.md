## Which independence is real, and who can forge what

* **(a), same box/UID:** separate invocation, private directory and HMAC protect
  against accidental path overlap and forgery by a party lacking the key. They do
  not protect against this subject account. Mode 0700/0600 is enforced but UID 1011
  owns both subject and recorder. The fixture reads the key, modifies a retained
  terminal event and re-signs it; verification remains `unverified`. This is an
  executed counterexample to the proposed independence claim. HMAC is symmetric
  authentication, not a publicly verifiable independent digital signature.
* **(b), mayor/Buster:** real ONLY if the subject's credentials cannot read/modify
  the remote keys, assignment/clock/observation/acceptance state, verifier or pinned
  authority. A mayor or Opus one-shot on this same account fails. No such external
  deployment/appointment/custody evidence was provided or created. An inbox can
  transport a receipt but cannot authenticate its origin by itself. A remote
  verifier must keep the HMAC key there; transporting it here destroys the boundary.
  An independent public-key signer is the natural later offline-verification route.
  It must observe trusted runner events, not blindly sign subject-supplied files.
* **(c), Git:** publication retains an object at the remote once accepted, not a
  trustworthy launch/uptake/acceptance clock. Commit/tag dates are caller-supplied;
  local reflogs are writable, and a clone does not obtain the remote reflog. A
  signed tag needs independently controlled signing authority first. This seat
  already has records write credentials. Neither push nor signature supplies missing
  prospective assignments or event coverage.

## Installed interface and exact meaning

`/home/forge/bin/receipt-attest prepare --state DIR --context FILE` creates a private
local key and one challenge. Context is JSON with `issuer_id`, full
`subject_seat_id`, `subject_session_id`, `assignment_manifest`, `effective_prompt`,
`subject_paths`, `expected_sources`. File paths are absolute. It snapshots prompt
and manifest bytes before accepting later claimed events. It exits 0 with
`status=prepared`, which means a local challenge was written, not evidence accepted.

`/home/forge/bin/receipt-attest issue --state DIR --challenge ID --evidence FILE`
accepts JSON `{ "events_file": "/absolute/events.jsonl" }`. The supported v1
participation window is exactly four ordered events: launch, prompt-consumed,
first-task, terminal. Their fields and a complete invocation example are in the
retained fixture source below. It checks the sealed subject/session/nonce, prompt
hashes, manifest, source-set equality and timestamp order, snapshots the supplied
bytes and signs the binding. It does **not** observe a process tree or prove actual
prompt uptake. Complete process coverage and omitted work remain unknown; four
valid records must never be sold as a whole-work census.

`/home/forge/bin/receipt-verify --state DIR --attestation FILE --subject-seat ID
--subject-session ID` authenticates against locally retained challenge/issuance
and evidence state, then records one consumption. **Stateful check:** calling it
again refuses replay. It is not an idempotent/read-only inspection API. Full seat
and actual session come from a future authoritative runtime binding, not the
subject strings in the attestation. No such production binding is installed here.

Issue/first check: exit **3**, `unverified`, `signature_valid=true`, `observed=false`,
`independent=false`, reason `shared-write-boundary` or `self-issued`. Refusal: exit 2.
Missing secret/evidence: exit 3, `unverified`, signature validity `unknown`. Verify
never initializes a missing key. Help exits 0 without mutation; malformed argv
refuses. Both names invoke the same isolated Python implementation; no shell eval,
request subprocesses, external crypto dependency, JVM or daemon. The shared
implementation is not an assertion of recorder/acceptor independence.

Default state is `/home/forge/.local/share/receipt-recorder-v1`; only disposable
fixture state was instantiated. It is excluded from tighten/records and absolute
path-valued `TIGHTEN_*` roots as well as declared subject roots. State/key modes,
symlinks, hardlinks, malformed and duplicate-key JSON, nonregular/oversize inputs
and unsafe challenge IDs are guarded. HMAC-SHA256 uses a random unpublished 32-byte
key, random key ID, full 256-bit challenge, canonical sorted compact ASCII JSON and
artifact-type domain separation. It binds issuer/key, challenge, subject seat/session,
launch and first-task hashes, effective-prompt/assignment-manifest/event-range
hashes, observed-consumption *claim* time, sealed/issued times, source set and the
shared-write limitation. Raw retained event-range hashing preserves exact bytes;
individual event hashes use the documented canonical JSON encoding.

Exclusive writes, fsync and flock serialize issue/check. Validation refuses before
reservation without changing existing bytes; after reservation an I/O failure may
leave partial state, reported as possible mutation. There is no automatic rollback
or reuse of a reserved challenge. Crash recovery and malicious rollback resistance
are not qualified; restoring old state can restore replay ability. No externally
anchored clock, revocation, anti-rollback service or production roster is claimed.

## Concrete v1 interfaces and scope

Two Python-standard-library one-shots, no JVM, network, daemon, or ports:

* `/home/forge/bin/receipt-attest prepare --state DIR --context FILE` seals one
  locally prospective assignment/session/challenge. Creates private state/key on
  first use. Context contains full `subject_seat_id`, `subject_session_id`,
  `issuer_id`, `assignment_manifest` and `effective_prompt` absolute file paths,
  `subject_paths` (nonempty absolute roots), and `expected_sources` (nonempty IDs).
* `/home/forge/bin/receipt-attest issue --state DIR --challenge ID --evidence FILE`
  snapshots JSONL launch, prompt-consumed, first-task and terminal events, each
  bound to the challenge, seat and session. Evidence JSON contains `events_file`.
  Events contain `kind`, `source`, `at` (UTC RFC3339), and the three binding IDs;
  launch/consumed events additionally bind `effective_prompt_hash`. Require that
  sequence, no extra event kinds, strictly ordered timestamps, and exactly the
  prospectively named source set. These are validations of supplied claims, not
  independent observations of the process tree. Retain exact supplied bytes.
* `/home/forge/bin/receipt-verify --state DIR --attestation FILE --subject-seat ID
  --subject-session ID` checks schema, authority consistency against the locally
  sealed challenge, MAC, full binding, retained bytes, issuance and time. It
  consumes a local challenge/session pair once even though the result remains
  unverified. A second check is `refused/replay`. This is a stateful check, not a
  read-only inspection. Missing key/state is `unverified/secret-absent` (exit 3),
  never key initialization. A copied attestation alone cannot prove freshness.

State default: `/home/forge/.local/share/receipt-recorder-v1`, outside tighten and

evidence input. No secret is accepted via argv or environment.

The canonical signed JSON body binds schema/domain, issuer/key ID, random
challenge, subject seat/session, assignment manifest hash, launch event hash,
effective prompt hash, consumption time, first task hash, covered event-range
hash, expected source set, sealed time, issued time, and `shared-write-boundary`.
HMAC-SHA256 over sorted compact ASCII JSON is domain-separated by artifact type.

retained state; this v1 provides no automatic deletion/retry bypass. Validation
refusals before reservation preserve bytes. Filesystem failures after reservation
report possible mutation. Replay protection assumes retained, unchanged state.
