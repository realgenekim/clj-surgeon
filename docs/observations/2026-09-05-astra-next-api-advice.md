# Astra advice: make complete decisions cheap

Recorded 2026-09-05T02:42:27.379521+00:00. This is the next experiment proposal, not an implemented API or an approved scoped implementation phase.

The primary measurement gives the investment case a concrete shape: on the same 21-owner task, six native/tool pairs per model yield median paired task-wall ratios 3.319× for Sol and 1.240× for Astra. Including measured server startup reduces these to 2.720× and 1.021×. Source: evidence/astra-primary-2026-09-05/report.md. A stronger native model already generates a single guarded Python rewrite; multiplying files does not multiply native model actions.

The follow-up makes both final checks explicit and lets the tool perform them inside its transaction. One pair per model finishes at native/tool 96.7/20.0 seconds for Sol and 50.3/19.4 for Astra; both tool callers take two outer actions. These are exploratory observations under changed proof policy, not a replicated causal improvement over the primary. Six optional callers subsequently choose the tool and use its final proof without rerunning it; one caller recovers an invalid profile. Source: /var/tmp/forge/astra-program/followup-proof-audit/{slice01-04,slice09,slice10-14}. The promising unit is a completed, verified decision.

The real application candidate exposes what remains expensive. Moving six related helpers requires a 37,300-byte request encoding 85 caller changes, 258 sites and 186 owners in 28 caller files. Twenty callers mix moved and retained helpers, so whole-library substitution is wrong. Preparation uses 22 retained MCP reads and 9.039 seconds of call wall; its interrupted envelope spans almost an hour and is not an active-time measure. Source: /var/tmp/forge/astra-program/application-extraction-preflight/direct-payload-v2/README.md. A fast final write alone would conceal this cost.

The next bounded public capability should accept selected helper identities, destination namespace, explicit caller alias policy and a named verification profile. Surgeon should derive the complete caller partition, retain unaffected uses, build one guarded transaction and return its terminal proof. A plan response is needed only when a real judgment remains: ambiguous ownership, unsupported binding grammar, incomplete reference scope, or a policy collision. Each such response should expose the specific unresolved decision and a bound continuation; a caller should not reconstruct hashes, counts, selectors or already-known facts.

The outcome contract must be honest: exact closure over named roots and supported syntax, preserved protected bytes and modes, final verification actually completed or explicitly pending, and no universal claim that arbitrary macros have been understood. Retire the original selected definitions in the acceptance fixture so successful compilation cannot hide unrewritten references. Unsupported binding defaults and parameter metadata must refuse safely until supported by explicit witnesses. A receipt saying atomic and parsed is weaker than behavioral equivalence.

The credible native competitor gets the same task facts and proof obligations, may use a parser or a six-name batch script, and may fuse writing and tests in one process. The new operation wins only if the full interval from receiving the task to accepted final proof shrinks. Count preparation, schema discovery, refusals, cold startup separately and inclusively. The first hand-drive must precede fresh caller measurement; calibrate the identical native control, freeze both prompts and a behavior oracle, and include optional adoption. Do not optimize a hand-built payload benchmark and call it problem-to-done.

My recommendation to Fable: finish the correctness repairs and measured test lanes, then implement this one six-helper closure only through the repository's design/requirements/tests/code workflow. Do not add a general natural-language task engine or several speculative verbs. The falsifier is straightforward: if a capable native batch script plus tests remains faster after equal setup, keep the structural proof as a quality option and stop selling it as a speed route. Tenfold whole-task gains remain a target, not a conclusion.

The long-lived process also matters. The primary Astra result is nearly neutral once startup is charged, so a request should arrive at an already-ready project service. That claim is architectural advice from the measured startup sensitivity, not evidence that this cohort measured steady-state hot caches. The API should expose real readiness and source identity rather than requiring callers to infer them from an installed tool name.

Success should retire uncertainty as well as edit text. The caller should be able to stop because the response names completed checks on the committed candidate. Conversely, a missing proof is missing even if an external benchmark judge later runs it. The first cohort exposed exactly that distinction: five Sol tool arms did not run the namespace-load command in-session. The follow-up bound both commands explicitly and audited the final successful receipts.
