## Blocking findings

### GATE-LANES-FENCE-001 — the worker bound is per coordinator, not box-wide

`machine-capacity` samples `MemAvailable` once and `gate-width` returns a local
executor width. Nothing reserves that memory or admits workers against other
coordinator processes. The installed `suite-run` intentionally permits three
concurrent suite processes using `suite-1.lock` through `suite-3.lock`; only
the battery path uses the exclusive `suite.lock`. Installed ship launches its
gate prewarm through `suite-run`, outside that exclusive lock.

Consequently a gate admitted at width 8 and a ship prewarm starting after it
can each own eight workers. This is not merely a simultaneous-read edge: the
retained gates reached a minimum `MemAvailable` of 18,524 MiB, at which the
formula still returns 8 on this 16-CPU box
(`floor((18524-2048)/1536)=10`, capped by `floor(16/2)=8`). The first pool's
future memory is not reserved, so the second admission treats it as available.
Two near-simultaneous admissions can do the same, and the three `suite-run`
slots permit a still larger aggregate.

The evidence establishes an eight-worker bound within one coordinator; it
does not establish the claimed shared bounded process coordination on the
loaded box where ship actually runs. Repair requires box-wide worker admission
or serialization shared by every gate entrance, plus a two-coordinator witness
that proves the aggregate worker and memory bounds. Admission-only
`MemAvailable` sampling is not that mechanism.

### GATE-LANES-FENCE-002 — land can consume an incomplete ship prewarm

The candidate makes `make test` delegate to `landing-gate`, whose coordinator
requires the alias suite. Installed ship still decomposes phase A as:

```text
make admit-transaction-recovery-battery mcp-test test-bb repository-hygiene
```

It omits `alias-migration-test`, and its `GATES_LANES` metadata omits it too.
Phase B runs only `battery-fresh`. Thus A+B is not this candidate's `make test`.

The receipt hash does not fail closed on that omission. Ship hashes the
`test`/`landing-gate` recipe plus its own `GATES_LANES` string. Land recomputes
the manifest hash using the receipt's own `lanes` field, not a gate membership
independently derived from the merged repository. A self-consistent incomplete
list therefore matches. If tree, toolchain, audit, and the suites that did run
are green, land reaches `CONSUME=1` and skips `make test`; the current-tree
alias battery then ran nowhere in the consumed landing path.

The safe consumption outcome for this candidate is **rerun**, with a typed
manifest/incomplete-coverage reason, until phase A includes the alias suite and
land compares the receipt against repository-derived required membership.
Recipe identity and exact tree binding do not prove that the recipe's
transitive gate was executed.
