## Blocking findings

### GATE-LANES-FENCE-001-R2 — deleting the slot directory creates a second live semaphore

The sampling/count/reservation race is closed only while every coordinator
opens the same `admission.lock` and slot-file inodes. `test/gate_slot.py`
places both kinds of lock inside `/var/tmp/forge/gate-slots/`. POSIX flock does
not prevent an owned path from being unlinked. If that directory is removed
while a worker holds a slot, the worker continues to lock the now-unlinked
inode; the next acquisition recreates the directory and locks a new
`admission.lock` and new `slot-0.lock`. Neither coordinator can see the other.

I executed the attack against an owned `/var/tmp/sol-slot-delete-*` root using
the production `try_acquire` function and a live width of one:

```text
{'first_held': True, 'root_removed': True, 'second_admitted': True,
 'derived_width': 1, 'bound_violated': True}
```

Both returned handles remained open simultaneously. This is the exact
split-inode failure the source comment warns about, but "never unlink" is only
an instruction to this helper; it is not enforced against another cleanup or
coordinator process. The admission flock, live MemAvailable resampling, and
occupied-slot count all occur after the split and therefore cannot repair it.

The existing five Python tests pass. They prove live shrink/growth, inherited
locks, nonzero exit, failed exec, and SIGKILL release, but contain no root
replacement or inode-continuity witness. The retained 2,655-sample two-gate run
proves an aggregate peak of eight in the no-deletion case only.

Repair requires a stable lock identity outside the removable slot directory
(or another kernel-visible box-wide semaphore), an executed root-removal
witness showing no second admission while the first handle lives, and a repeat
of the two-coordinator bound witness. That changes `test/gate_slot.py` and its
oracle. The ship-fix contract says a fix deleting lines under `test/` is
`HOLD reason=oracle-changed`; this is therefore not an eligible small
`GO-WITH-FIX` patch.

### GATE-LANES-FENCE-002-R2 — installed ship cannot consume this producer's prewarm receipt

The repository half of the repair is internally consistent. The retained
prewarm receipt has these targets, all exit zero:

```text
admit-transaction-recovery-battery
alias-migration-test
mcp-test
test-bb
repository-hygiene
intent-audit
```

Adding `battery-fresh` exactly equals `make -s print-gate-stages`. The retained
full receipt's seven targets also exactly equal the printed set. Both execution
and printing derive from `gate-stage-manifest`.

The installed ship v3.5 handoff nevertheless looks for
`target/landing-gate.edn`, while this candidate's prewarm deliberately deletes
that path and writes `target/landing-gate-prewarm.edn`. Ship therefore falls
back to parsing its command, which yields only `landing-gate-prewarm`; unioned
with phase B, it reports only `landing-gate-prewarm battery-fresh`. Installed
land correctly compares that set with the merged tree's seven-stage manifest
and reruns with `reason=stage-set-mismatch`.

Changing only the configured path would still not consume: ship's `sed`
expression treats the receipt as a flat vector of strings, but the actual
`:stages` value is a vector of maps containing `:target`, `:exit`, and
`:wall-ms`. It would include map keys and numeric values in the alleged stage
set. Thus the expected outcome for this branch under the installed defaults is
**rerun**, not consume. This fails closed and cannot authorize an incomplete
landing, but it does not deliver the claimed consumable prewarm. The installed
script is outside this review worktree, so no eligible self-applied repository
patch can close it here.
